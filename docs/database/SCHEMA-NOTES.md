## ADR-059: Simplified Context Model (Current Schema)

**Tables** (use these names, not legacy):
- `platform_connections` (not `user_integrations`)
- `platform_content` — **DROPPED (ADR-153)**. Was unified content layer with retention (ADR-072). Platform data now flows through tasks into workspace context domains.
- `filesystem_documents` / `filesystem_chunks` — uploaded documents only
- `user_memory` — single Memory store (replaces knowledge_profile, knowledge_styles, knowledge_domains, knowledge_entries)
- `agents` — persistent workforce roster. Identity-only: `role`, `title`, `scope`, `status`, `type_config`, `agent_instructions`, `agent_memory`, `origin`. No schedule, no destination, no mode — those live on tasks. **ADR-205 (2026-04-22):** signup scaffolds exactly ONE row — YARNNN (role=`thinking_partner`, origin=`system_bootstrap`). Specialists (researcher/analyst/writer/tracker/designer/executive) lazy-create on first dispatch via `services.agent_creation.ensure_infrastructure_agent()`. Platform Bots (slack_bot/notion_bot/github_bot/commerce_bot/trading_bot) materialize on OAuth connect and delete on disconnect (connection-bound lifecycle). User-authored Agents use `origin='user_configured'` and are unchanged. The user-facing `/agents` list filters by `origin != 'system_bootstrap'` per ADR-189.
- `tasks` — **thin scheduling index** post-ADR-231 D4 Path B (migration 164). Columns: `id, user_id, slug, status, schedule, next_run_at, last_run_at, created_at, updated_at, declaration_path, paused`. The `mode` and `essential` columns dropped. Authoritative recurrence-declaration substrate is workspace_files YAML at `declaration_path` (e.g., `/workspace/reports/{slug}/_spec.yaml` for DELIVERABLE shape). The table is fully reconstructable from filesystem state via `services.scheduling.materialize_scheduling_index()`. The table name "tasks" identifies the SCHEDULING INDEX, not work substrate. **`/tasks/{slug}/` filesystem tree DELETED per ADR-231 D2.** Per-shape natural-home paths per D2/D3: DELIVERABLE → `/workspace/reports/{slug}/_spec.yaml` + `/workspace/reports/{slug}/{date}/output.md`; ACCUMULATION → entry in `/workspace/context/{domain}/_recurring.yaml`; ACTION → `/workspace/operations/{slug}/_action.yaml`; MAINTENANCE → entry in `/workspace/_shared/back-office.yaml` + audit log at `/workspace/_shared/back-office-audit.md`.
- `agent_runs` — execution audit trail per agent (was `deliverable_versions`, renamed ADR-103). ADR-118 D.3: dual-write (content still written for frontend compat), but delivery reads from workspace_files output folders. Will become pure audit trail when frontend migrates.
- `agent_type` — column on `agents` table, **DEPRECATED** by ADR-109 — being replaced by `scope` + `role`
- `agent_instructions` — column on `agents` table, **DEPRECATED** by ADR-106 Phase 2 — migrated to workspace `AGENT.md`. No longer written for new agents. DB column kept only for lazy migration of pre-workspace agents via `ensure_seeded()`. Workspace AGENT.md is sole authority.
- `agent_memory` — column on `agents` table, **DEPRECATED** by ADR-106 Phase 2 — migrated to workspace `memory/*.md`. No longer written for new agents. Workspace memory files are sole authority.
- `workspace_files` — virtual filesystem for agent workspaces (ADR-106); path-based access, full-text + vector search; `content_url` column for rendered binary files (ADR-118). ADR-118 Phase D: becomes the single output substrate for all agent outputs (text + binary), replacing agent_runs as the delivery source. ADR-119: adds `version` + `lifecycle` columns; folder conventions (output folders with `manifest.json`, project folders, ephemeral `/working/`) replace relational grouping tables. **ADR-209 (2026-04-23)**: adds `head_version_id` pointer column + two sibling tables for the Authored Substrate: `workspace_blobs` (content-addressed CAS keyed by sha256) and `workspace_file_versions` (parent-pointered revision chain with required `authored_by` + `message` attribution). `ADR-119 Phase 3 /history/` subfolder convention superseded — versioning moves from filesystem namespace to substrate-native revision chain. `version` integer column scheduled for drop in ADR-209 Phase 5.
- `workspace_blobs` — ADR-209 Authored Substrate: content-addressed immutable store keyed by sha256. Shared across workspaces (identical content reuses one blob). No user-level scoping — scoping lives at the revision layer.
- `workspace_file_versions` — ADR-209 Authored Substrate: parent-pointered revision chain per `(workspace_id, path)` (ADR-373 Phase 1 Implemented — the workspace is the binding unit via `authored_substrate.py::_substrate_scope`; `(user_id, path)` is the N=1 fallback). Every mutation to `workspace_files` produces exactly one row here. `authored_by` taxonomy: `operator` | `yarnnn:<model>` | `agent:<slug>` | `specialist:<role>` | `freddie:<identity>` (the live prefix since the 2026-06-29 full rename; legacy rows carry `reviewer:<identity>`) | `member:{user_id} via {model}` (ADR-411 D4 lane writes) | `system:<actor>`. `parent_version_id` is NULL on the first revision for a path; forms a walkable DAG. **`revision_kind` column (ADR-423, migration 208, Implemented 2026-07-08):** `authored` (default — an ordinary revision; all pre-migration rows read this, no backfill) | `observation` (a retained raw intake — the 3 intake writers [MCP `remember`, connector capture via `_write_if_changed`, `TrackWebSources` raw write] tag it) | `derivation` (a derived act citing its sources — first live writer: the ADR-395 upload projection, per ADR-448; the MCP-remember derive step is still prompt-only). This is what lets the `inbound/` directory dissolve — a raw arrival is marked by its `revision_kind`, not its path, so the two raw lanes unify under one operator-facing **Downloads** zone (the Files-model note, `docs/analysis/the-files-model-directory-is-meaning-everything-else-is-metadata-2026-07-08.md`). `write_revision(revision_kind=...)` threads it; only written when non-default (byte-identical authored writes). **`derived_from` column (ADR-448, migration 215, Implemented 2026-07-12):** JSONB list of absolute workspace paths — the REFERENCE EDGE (what this revision was made from). Written when a caller passes `derived_from=` (a declared derive act → kind defaults to `derivation`) or LIFTED at the write door from the two content conventions (head-anchored `derived_from:` frontmatter → edge + kind; artifact `data-ref` citations in `.html` → edge only). Readers: `list_revisions`/`read_revision`/`trace` (column-first, content-scan legacy fallback) + `authored_substrate.list_dependents` (which HEADs cite a path — serves `GET /api/workspace/file/dependents` + the Files delete-confirm "N files were made from this" warning). Edges are historical facts, never live FKs (a move doesn't rewrite the ledger). This is the load-bearing-files axiom made structural: importance is a GRAPH position (legibility=edges, protection=powerbox grants, version-coupling=data-ref pins), never a folder class — see the load-bearing-files note + [ADR-448](docs/adr/ADR-448-the-reference-edge-derived-from-on-the-ledger.md). **ADR-373 (Phase 1 Implemented — corrected 2026-07-09, was mislabeled "not yet Implemented"):** the substrate's binding unit moves from `(user_id, path)` to `(workspace_id, path)` — `workspaces` table + a `workspace_id` FK; `user_id` relocates to a `principal_grants` membership/authorization fact. The 1:1 world is the N=1 case (backfill: each `user_id` → a singleton owner-workspace, byte-identical behavior). The workspace becomes a **multi-principal** attributed commons (humans, their agents, other humans, platforms, foreign/local LLMs each attribute as themselves); per-principal grant reinterprets `CALLER_WRITE_POLICY` as class-defaults; single-writer-per-path (ADR-286) means **no merge/CRDT layer** — semantic conflict is reconciled by the workspace-level Reviewer seat. **Migrations `189_adr373` (principal_grants + workspace_id FK + N=1 backfill) / `198_adr373` (member write-scope) / `199_adr404` (invites) are in-tree; `_substrate_scope` keys the chain on `workspace_id`.** Additive-remaining: richer member-provisioning UX. See [ADR-373](docs/adr/ADR-373-multi-principal-workspace-and-the-re-key.md).
- `workspaces` / `principal_grants` — **ADR-373.** `workspaces` = the substrate's binding unit (the re-key target). `principal_grants(principal_id, workspace_id, role, scopes, granted_by, status)` = the per-principal authorization fact; `role` ∈ `owner | member | own-agent | foreign-llm | platform | a2a`; `scopes` defaults to the role's class-default (the reinterpreted `CALLER_WRITE_POLICY`). Member/own-agent slots ship in-schema at launch; their provisioning UX is additive post-launch (D4). **GRANT-CONSULT IMPLEMENTED 2026-06-29 (Phase 2)** — the gate now authorizes at PRINCIPAL granularity. `services/supabase.py::resolve_principal_id(auth)` is the uniform principal-id abstraction (owner→`user_id`, **foreign-llm→PROVIDER host-id** [ADR-373 D2.a, 2026-06-30 — NOT the OAuth `client_id`; see below], agent→slug); `services/primitives/workspace.py::_is_path_locked_for_principal(auth, path)` reads the active grant's `scopes` (allow-list narrowing) **else falls back to the class-default `_is_path_locked`** = today's behavior (the safety invariant — owner/NULL-scope is byte-identical, proven 99/0 across all 11 live owner grants; D2.a changed ONLY the `yarnnn:mcp*` branch, owner path untouched). Both gate sites in `permission.py` (MCP branch + Reviewer branch) route through it. `AuthenticatedClient` carries `principal_id` (the 3rd field). **POLARITY**: `CALLER_WRITE_POLICY` lists LOCKED prefixes; grant `scopes` lists ALLOWED regions (complements) — `_is_path_locked_for_principal` handles the inversion. Per-request memoized; the lookup hits `uq_principal_grant_active`. Adjacent fix (same session): the MCP topology lock was DORMANT — the exact `== "yarnnn:mcp"` matcher in `_caller_class`:1768 + `permission.py`:257 missed the live room-qualified `yarnnn:mcp:<client>` form, so foreign-LLM writes to locked roots fell to the non-reviewer free-pass; fixed to `startswith`, activating the ADR-320-intended lock. Read-only **Workspace Members** legibility panel at `web/components/workspace-concepts/WorkspaceMembersCard.tsx` (Workspace Settings → Access) over `GET /api/workspace/members`. Regression: `api/test_adr373_grant_consult.py` (20/20). This satisfies the ADR-384 §7 re-founding prerequisite. **GRANT LIFECYCLE — ADR-386 IMPLEMENTED 2026-06-29 (+ D1.a amendment 2026-06-30).** The consult *reads* grants; ADR-386 *creates + governs* them. `services/principal_grants.py`: `ensure_principal_grant` (idempotent auto-provision), `narrow_grant` (tighten scopes; reject owner), `evict_principal` (REVOKE = full eviction — grant→`revoked` + delete OAuth tokens by client_id; reject owner). **Foreign-LLM auto-provision** fires on BOTH OAuth token-mint paths (`mcp_server/oauth_provider.py::_ensure_foreign_llm_grant`, one shared helper): `exchange_authorization_code` (`system:oauth-connect`) AND `exchange_refresh_token` (`system:oauth-refresh`, **D1.a** — the durable fix; authorize-only left the entire already-connected population grant-less + invisible because live connectors stay alive via silent refresh rotation and never re-authorize). Best-effort (a grant failure never breaks OAuth). **One-time backfill** `scripts/oneshot/adr386_backfill_foreign_llm_grants.py` ensured the live population (receipt 2026-06-30: 0→7 `foreign-llm` grants, 2 ChatGPT + 5 Claude, all → workspace `d5b9029b`, owner grants untouched; idempotent re-run held at 7). Two operator verbs: `POST /api/workspace/members/{principal_id}/{narrow,revoke}` (owner-immutable → 403, D4). The **AI Connections** pane (Channels surface, slug `external-agents`; relabeled from "External Agents" 2026-06-30, relabel-keep-slug) is a role-filtered (`foreign-llm|a2a|platform`) view of the same roster. Regression: `api/test_adr386_member_lifecycle.py` (31 + 3 mcp-gated helper tests — `@_requires_mcp` skip under the 3.9 api venv, run under `.venv-mcp` 3.11). `member`/`own-agent`/`platform`/`a2a` stay name-only — `member` blocked by the unfinished ADR-373 substrate re-key (`user_id→workspace_id`), NOT demand (D6). **PROVIDER-AS-MEMBER — ADR-373 D2.a (2026-06-30).** The foreign-LLM `principal_id` is the **stable provider host-id** (`chatgpt` / `claude.ai` / …, resolved via the ADR-379 `mcp_server/presentation/hosts.py::resolve_host_id` registry — the SINGLE identity resolver, CI-gated against leaks), **NOT the OAuth `client_id`** — which a connector re-mints on every re-registration (DCR), fragmenting one provider into many dead grant rows (the live AI Connections roster showed "Claude" 5× / "ChatGPT" 2×). One provider = one grant per workspace, across all `client_id` re-registrations. `services/principal_grants.py`: `resolve_provider_id`/`resolve_provider_id_for_client` (client signals → host-id, strongest-first: client_name → client_id → **redirect_uri** [the strong signal for claude.ai, whose registered name is bare "Claude"]), `client_ids_for_provider` (eviction sweeps ALL of a provider's tokens, since the grant key is now a host-id with no matching token row), `provider_label` (host-id → friendly name). The consult resolves the MCP caller to its provider, so **a narrow binds the provider across ALL sessions incl. future reconnects** — closing a latent narrow-escape bug (pre-D2.a, a reconnect's new client_id escaped the narrow). Migration `scripts/oneshot/adr373_d2a_rekey_provider_grants.py` collapsed the live 7 client_id grants → 2 provider grants (`chatgpt`/`claude.ai`; the 7 old rows → `revoked` audit, reversible, tokens untouched; receipt 2026-06-30, idempotent re-run = no-op). The backfill script keys on provider too. Regression: `api/test_adr373_grant_consult.py` D2.a block (host-id-over-client_id, reconnect→same provider, owner byte-identical) + `test_adr386` provider tests; ADR-379 gate 10/10 (no host-name leak). **CONNECTING-MEMBER OWNS THE GRANT — ADR-431 IMPLEMENTED 2026-07-09 (migration 209).** With multiple humans in one workspace each connecting their own ChatGPT/Claude, `(provider, workspace)` collapsed distinct members' connections into one row (the D2.a provider-key was correct at N=1 but member-blind at N>1 — `ensure_principal_grant` no-op'd the second member onto the first). Fix: the relational unit widens to **`(provider, connecting-member, workspace)`** — new `principal_grants.connected_by UUID` (the human who authorized the connection; NULL/redundant for owner/member/own-agent). `uq_principal_grant_active` → `(principal_id, workspace_id, COALESCE(connected_by::text, principal_id))` so human/agent grants stay singletons (byte-identical) while two members' same-provider connections coexist. `ensure_principal_grant`/`narrow_grant`/`evict_principal`/`_load_active_grant` thread `connected_by`; `_ensure_foreign_llm_grant` records the OAuth session `user_id`; the gate consult (`_lookup_grant_scopes`) keys `connected_by = auth.user_id` for external principals with a **MEMBER-FIRST, PROVIDER-WIDE FALLBACK** (prefer the member's own grant, else the NULL-connected legacy grant — preserves every pre-431 grant + owner byte-identity); `delete_tokens_for_client(client_id, user_id)` scopes eviction to the member (revoking seulkim's ChatGPT leaves the owner's connected); `cascade_member_ai_connections` (D5) revokes a departing member's AI connections. `GET /workspace/members` returns `connected_by` + `connected_by_label` ("your connection" / the member's email); `WorkspaceMembersCard` splits **People / AI connections** with a per-AI-row "· connected by {email}" sub-label. The A2 chat model (Sonnet/Gemini via the router) is NOT a principal and never on the roster — it writes as `member:{user} via {model}` under the member's grant (ADR-408 A2). Regression: `api/test_adr431_connecting_member.py` 7/7; ADR-373 25/25 + ADR-386 12/12 still green; live-DB coexistence + dup-reject verified.
- `workspace_file_versions` — NOT a table; version history uses `/history/` subfolder convention (ADR-119 Resolved Decision #3). On overwrite of high-value files (thesis.md, memory/*.md, AGENT.md), previous version copied to `/agents/{slug}/history/{filename}-v{N}.md`. Implemented in Phase 3.
- `mcp_oauth_clients` / `mcp_oauth_codes` / `mcp_oauth_access_tokens` / `mcp_oauth_refresh_tokens` — MCP OAuth 2.1 storage (ADR-075, service key only)
- `render_usage` — **DROPPED (ADR-417, migration 207)** — per-user render call tracking (ADR-118 D.2); was already a fossil under ADR-172/396's one-meter billing. Retired with the render service.
- `wake_queue` — **ADR-298 transient compute, not authoritative state** (migration 179, ADR fully Implemented 2026-05-22). Per-workspace queue for single-lane Reviewer execution with two-lane drain (paced/live). Mechanically reconstructable from filesystem + DB substrate at every moment per Axiom 1; modeled on `tasks` scheduling-index precedent (ADR-231 D4). UNIQUE `(user_id, wake_source, dedup_key)` enforces cross-source dedup at insert time — the **singular dedup surface** post-Phase 5 (legacy `execution_events.wake_dedup_key` column dropped via migration 180 + walker pre-check + telemetry kwarg removed in commit `dc36cdf`). Status taxonomy: `pending → locked → completed | failed | dropped`. RLS service-role-only; operators do NOT read queue directly — they read configuration (yaml), outcomes (feed + `execution_events`), and watch-state (`standing_intent.md`). Service helpers in `api/services/wake_queue.py`.
